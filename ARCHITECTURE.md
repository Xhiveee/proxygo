# Архитектурные решения

## Глобальная идея

Пинг растёт не из-за «богатого» бэкенда, а из-за транзитного маршрута РФ→Германия
(bufferbloat + потери на магистралях). Решение — спрятать РЕАЛЬНОГО игрока за
фронтендом в РФ и дать бэкенду в DE знать настоящий IP игрока. Задача делится на
две независимые части, общающиеся только по PPv2:

* **Go-прокси** принимает игру в РФ, добавляет PPv2 заголовок, гонит байты в DE.
* **Java-агент** на сервере читает PPv2 и «подставляет» IP в Minecraft.

## Почему TCP — PPv2, а UDP — прозрачный

Voice Chat моды (Simple Voice Chat, Plasmo Voice) авторизуют игрока по UUID из
TCP-сессии, а не по IP. Поэтому для UDP PPv2 не нужен и вреден — он лишь усложнил бы
разбор пакетов в модах. Достаточно прозрачно форвардить датаграммы. Для TCP PPv2
включает реальный IP, что критично для антидюпов/мониторинга.

## PPv2 заголовок

`pkg/ppv2` формирует бинарный заголовок v2 (Java-агент парсит по спецификации).
Поддерживаются IPv4/IPv6, команда PROXY, протоколы STREAM(TCP)/DGRAM(UDP). Если
адрес не удалось получить — заголовок деградирует до семьи UNSPEC (без блока
адресов), сервер всё равно обрабатывает его как прозрачный.

## UDP-маппинг сессий

Каждый клиент IP:порт получает отдельный upstream-сокет. Это даёт:
* демуксплекс ответов бэкенда по порту источника;
* таймаут неактивности 60с (сессия самозакрывается в readLoop);
* изоляцию потоков — один клиент не влияет на чужой.

Используется **неcвязанный** сокет (`ListenUDP` + `WriteTo/ReadFrom`), а не
`DialUDP`. Причина: на Windows связанный UDP-сокет не получал ответ бэкенда на
loopback (проверено тестом), несвязанный — работает стабильно и на Linux, и на
Windows.

## Надёжность и скорость

* `io`-копирование с буфером 32KB (из конфига), ядро+O_Copy не нужно.
* Idle-таймаут: обёртка `countConn` обновляет дедлайны при каждом чтении/записи,
  так что тихая половина стрима не «убивает» активную.
* Общая статистика пишется в `stats_hourly` дельтами (флашер раз в минуту),
  поэтому повторные сэмплы не задваивают счётчики.

## Graceful shutdown / drain

`Backend.shutdown(grace)` закрывает listener (приём останавливается), ждёт пока
активные TCP-соединения рассосутся до `grace` (30с), а затем принудительно
закрывает оставшиеся сокеты. Это позволяет игрокам договорить во время
перезагрузки/удаления бэкенда.

## Хранение состояния

SQLite через `modernc.org/sqlite` (pure-Go, без CGO) — важно для кроссплатформенной
сборки и Docker. `maxOpenConns=1` + WAL + `busy_timeout` решают проблему
одно-писателя. Активные соединения держатся только в памяти, в БД — бэкенды,
баны, почасовая статистика и аудит-лог.

## Безопасность

* Whitelist Telegram admin-IDs + rate limit 10/мин (token bucket).
* `backend_whitelist` (IP/CIDR) — защита от SSRF (в `/add` проверяется).
* Max TCP-подключений на IP (глобальный трекер) и max UDP-пакетов/сек на IP.
* DDoS-детект через per-IP минуты: >100 TCP/мин или >1000 UDP/мин → разовая
  телеграм-алерт (не чаще 1/мин, чтобы не спамить).
* Баны: SQLite (источник истины) + best-effort зеркало в iptables.

## Telegram как конфигуратор

Прокси не перезапускается при изменениях: `/add`, `/remove`, `/add-udp`,
`/restart` работают поверх работающего Manager (hot-reload). Удаление — с
confirm-кнопкой в inline-клавиатуре. `/stats` — с кнопкой refresh.

## Java-агент

Инжекция в `channelRead/channelRead0` (не в `channelActive`): на момент активации
канала данные ещё не пришли, заголовка нет. Поля ищутся **по типу**
(`InetSocketAddress`), а не по имени — это устойчиво к обфускации и MCP-маппингам.
Всё обёрнуто в try/catch: если PPv2 невалиден или поле не найдено — сервер
работает дальше, агент молчит.

## Известные ограничения

1. PPv2 заголовок должен прийти одним TCP-сегментом (обычно так и есть); при
   экстремальной сегментации агент ждёт следующих байт (не помечен done).
2. Агент подменяет адрес рефлексией — на Java 17+ с модулями без export
   (нетипично для серверов на classpath) может не получиться.
3. `enforce_iptables` требует `CAP_NET_ADMIN`/root; без него работает только
   внутренний ACL.
4. `stats_hourly` округляет трафик по часу на момент флаша — переход через
   границу часа учитывается в «текущем» часе.
5. TCP idle-таймаут (30м) в итоге закроет зависшие соединения — параметр
   настраивается.
6. Один frontend-порт на бэкенд; мульти-IP/порт в DE — это несколько бэкендов в
   Manager (поддерживается).
