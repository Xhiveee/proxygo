# Архитектурные решения

## Общая идея

Прокси прячет реальный IP игрока за фронтендом и передаёт его бэкенду. Две
независимые части, общающиеся только по PPv2:

* **Go-прокси** принимает подключения, добавляет PPv2 заголовок, гонит байты к бэкенду.
* **Java-агент** на сервере читает PPv2 и подменяет remote address.

## Почему TCP — PPv2, а UDP — прозрачный

Голосовые моды авторизуют игрока по UUID из TCP-сессии, а не по IP, поэтому для UDP
PPv2 не нужен — достаточно прозрачно форвардить датаграммы. Для TCP PPv2 передаёт
реальный IP (нужно для мониторинга/антидюпов).

## PPv2 заголовок

`pkg/ppv2` формирует бинарный заголовок v2 (агент парсит по спецификации).
Поддерживаются IPv4/IPv6, команда PROXY, протоколы STREAM(TCP)/DGRAM(UDP). Если адрес
не удалось получить — заголовок деградирует до семьи UNSPEC (без блока адресов),
сервер обрабатывает его как прозрачный.

## UDP-маппинг сессий

Каждый клиент IP:порт получает отдельный upstream-сокет: демуксплекс ответов по порту
источника, таймаут неактивности 60с (самозакрытие в readLoop), изоляция потоков.
Используется **неcвязанный** сокет (`ListenUDP`+`WriteTo/ReadFrom`), а не `DialUDP`:
на Windows связанный UDP-сокет не получал ответ бэкенда на loopback (проверено тестом),
несвязанный стабилен и на Linux, и на Windows.

## Надёжность и скорость

* Копирование с буфером 32KB (из конфига).
* Idle-таймаут: обёртка `countConn` обновляет дедлайны при каждом чтении/записи —
  тихая половина стрима не «убивает» активную.
* Статистика пишется в `stats_hourly` дельтами (флашер раз в минуту) — повторные
  сэмплы не задваивают счётчики.

## Graceful shutdown / drain

`Backend.shutdown(grace)` закрывает listener, ждёт, пока активные TCP-соединения
рассосутся до `grace` (30с), затем принудительно закрывает оставшиеся сокеты —
активные соединения завершают работу во время перезагрузки/удаления бэкенда.

## Хранение состояния

SQLite через `modernc.org/sqlite` (pure-Go, без CGO). `maxOpenConns=1` + WAL +
`busy_timeout` решают проблему одно-писателя. Активные соединения — только в памяти;
в БД — бэкенды, баны, почасовая статистика и аудит-лог.

## Безопасность

* Whitelist Telegram admin-IDs + rate limit 10/мин (token bucket).
* `backend_whitelist` (IP/CIDR) — защита от SSRF.
* Max TCP-подключений на IP и max UDP-пакетов/сек на IP.
* DDoS-детект по per-IP минутам (>100 TCP/мин или >1000 UDP/мин) → разовая
  телеграм-алерт (не чаще 1/мин).
* Баны: SQLite (источник истины) + best-effort зеркало в iptables.

## Telegram как конфигуратор

Прокси не перезапускается при изменениях: `/add`, `/remove`, `/add-udp`, `/restart`
работают поверх работающего Manager (hot-reload). Удаление — с confirm-кнопкой,
`/stats` — с кнопкой refresh.

## Java-агент

Инжекция в `channelRead/channelRead0` (не в `channelActive`): на момент активации
канала данных ещё нет. Поле ищется **по типу** (`InetSocketAddress`), а не по имени —
устойчиво к обфускации и MCP-маппингам. Всё в try/catch: если PPv2 невалиден или поле
не найдено — сервер работает дальше, агент молчит.

## Известные ограничения

1. PPv2-заголовок должен прийти одним TCP-сегментом; при экстремальной сегментации
   агент ждёт следующих байт (не помечен done).
2. Подмена адреса рефлексией — на Java 17+ с модулями без export (нетипично для
   серверов на classpath) может не получиться.
3. `enforce_iptables` требует root/`CAP_NET_ADMIN`; иначе работает только внутренний ACL.
4. `stats_hourly` округляет трафик по часу на момент флаша — переход через границу
   часа учитывается в «текущем» часе.
5. TCP idle-таймаут (30м) в итоге закроет зависшие соединения — параметр настраивается.
6. Один frontend-порт на бэкенд; несколько бэкендов — это несколько записей в Manager.
